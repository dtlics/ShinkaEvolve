# Azure prompt caching & concurrency audit — mutation-call fan-out feasibility

## 1. Our client stack (as-read)

- **API surface: Responses API, not chat completions.** Both clients build `base_url = <resource>/openai/v1` so the SDK hits `/openai/v1/responses` (`shinka/llm/client.py:1-5,26-30`). Sync/async foreground path calls `client.responses.create(...)` with `input=[{"role":"system",...}, *history]` (`shinka/llm/providers/openai.py:118-125,177-184`). API version env default is `"preview"` (`shinka/llm/client.py:41,46`).
- **Background-poll transport** (`orchestrator/scripts/_azure.py:99-125`): `responses.create(model=<deployment>, instructions=system_msg, input=user_msg, background=True, reasoning={"effort":...}, metadata={...}, max_output_tokens=...)`, then `responses.retrieve(rid)` every 3s (`_POLL_INTERVAL_SEC=3.0`, `_azure.py:23`) up to a 3600s wall (`_azure.py:29`). All inner-loop mutation/fix/meta calls go through this (`orchestrator/scripts/mutate.py:242-246`, `meta_summarize.py:445`).
- **Models**: deployments `gpt-5.5`, `gpt-5.4-pro` (East US 2 only, `client.py:23,38-43`), `gpt-5.3-codex`, `gpt-5.4-mini` (CLAUDE.md deployment table).
- **Dispatch today is sequential**: `run_window.py` calls `mutate.main(...)` inline, one candidate at a time (`orchestrator/harness/run_window.py:508,844`). There is **no concurrent fan-out anywhere yet** (no threads/asyncio/pools around the mutate path) — this audit is prospective.
- **Absence findings**: `prompt_cache_key`, `prompt_cache_retention`, `store`, `previous_response_id`, `user`/`safety_identifier` are set **nowhere** in the fork (grep over the whole worktree — zero hits). Cost accounting reads only `input_tokens`/`output_tokens` (`_azure.py:73-74`, `openai.py:64-70`); `calculate_cost(model, in, out)` has no cached-token rate (`shinka/llm/providers/pricing.py:118-138`) and `pricing.csv` has no cached-price column (header: `model_name,provider,input_price,output_price,input_price_tier2,output_price_tier2,tier_threshold,...`). **Nothing in the ledger models the cached-input discount** — see §7.

## 2. Prompt caching on Azure OpenAI

Source: [MS Learn — Prompt caching with Azure OpenAI](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/prompt-caching) (updated 2026-06-05). All VERIFIED unless flagged.

- **Which models**: "All Azure OpenAI models GPT-4o or newer support in-memory prompt cache retention" — covers all four of our deployments. **Extended (24h) retention** is listed for `gpt-5.4`, `gpt-5.3-codex`, `gpt-5.2`, `gpt-5.1*` (incl. codex/chat variants), `gpt-5`, `gpt-5-codex`, `gpt-4.1`; for models **newer than gpt-5.4** (i.e., our `gpt-5.5`) "the default is `24h` and `in_memory` isn't supported". Retention is configurable per request via the `prompt_cache_retention` parameter (allowed values `in_memory` / `24h`; for `gpt-5.4` and older the default is `in_memory`). `gpt-5.4-mini` and `gpt-5.4-pro` are **not** in the extended list — UNCERTAIN whether they get 24h retention; assume in-memory only. Notably, [OpenAI's pricing page](https://developers.openai.com/api/docs/pricing) lists **no cached-input price for gpt-5.4-pro** (a dash where other models show a price) — pro likely gets no caching discount at all (Azure-side confirmation UNCERTAIN).
- **Automatic, no opt-out**: "Prompt caching is enabled by default … There's no opt-out support."
- **Minimums/granularity**: request ≥ **1,024 tokens** and the **first 1,024 tokens identical**; after that, "cache hits occur for every 128 additional identical tokens." A single-character difference inside the first 1,024 tokens ⇒ full miss (`cached_tokens: 0`).
- **Routing**: "Requests are routed based on a hash of the initial prefix of a prompt. The hash typically uses the first 256 tokens, though the exact length varies depending on the model." `prompt_cache_key` is combined into that hash to steer co-routing. Above **~15 requests/min per prefix+key**, overflow spills to extra machines, "reducing cache effectiveness" — each new machine is a one-time miss (quantified identically in [OpenAI Prompt Caching 201](https://developers.openai.com/cookbook/examples/prompt_caching_201)).
- **TTL**: in-memory caches clear "within 5 to 10 minutes of inactivity and always … within one hour of the cache's last use"; extended retention up to **24 hours** (KV tensors offloaded to GPU-local storage when memory is full).
- **Scoping**: "The system doesn't share prompt caches between Azure subscriptions" — subscription is the only documented isolation boundary. Whether two deployments of the same model in one subscription/region share cache is **undocumented — UNCERTAIN**. Our westus/eastus2 split means pro traffic can never share cache with the westus models regardless.
- **Pricing**: Azure states cached tokens are "billed at a discount on input token pricing" for Standard, "up to 100% discount" for Provisioned, and "prompt cache pricing is the same for both retention policies" — but the Azure doc gives **no number**. [OpenAI's pricing page](https://developers.openai.com/api/docs/pricing) lists cached input at **10% of input price** (gpt-5.5: $0.50 vs $5.00/1M; gpt-5.4-mini: $0.075 vs $0.75; gpt-5.3-codex: $0.175 vs $1.75). Exact Azure Standard numbers: **UNCERTAIN — check the [Azure pricing page](https://azure.microsoft.com/pricing/details/cognitive-services/openai-service/); do not assume parity.**
- **What's cached**: full messages array (system/developer/user/assistant), images, **tool definitions**, structured-output schemas ("appended as a prefix to the system message"). Best practice: "structure your requests so that repetitive content occurs at the beginning."

## 3. Concurrency + cache

- **Cold start**: no official doc states it outright, but [Prompt Caching 201](https://developers.openai.com/cookbook/examples/prompt_caching_201) establishes the mechanic — requests are routed to inference engines by prefix hash, and a machine that hasn't prefilled the prefix is a one-time miss. N simultaneous first requests dispatch before any completes prefill ⇒ **all N miss** (VERIFIED mechanic, inferred consequence).
- **Warm-then-fan-out is an inference, NOT a documented pattern.** [CORRECTED] Neither the Prompt Caching 201 cookbook nor the [OpenAI prompt-caching guide](https://developers.openai.com/api/docs/guides/prompt-caching) recommends sending one request to warm the cache before fanning out concurrent requests (both checked; the quotes previously attributed to the cookbook do not appear in it). It nonetheless follows directly from the cold-start mechanic above: send one mutation, await its `completed`, then dispatch the rest with a shared `prompt_cache_key`. Treat as sound engineering inference, not vendor guidance.
- **Rate ceiling**: keep each prefix+`prompt_cache_key` combination under **~15 RPM** (VERIFIED — the prompt-caching guide advises "Select a granularity that keeps each unique prefix-`prompt_cache_key` combination below 15 requests per minute to avoid cache overflow"). Our realistic fan-out (2–8 concurrent mutations, each running minutes) is far below this; overflow is a non-issue.

## 4. Responses API background mode

- **`background=true` requires `store=true`** — "Background sampling requires store=true; stateless requests are rejected" ([OpenAI background guide](https://developers.openai.com/api/docs/guides/background), VERIFIED). Our `bg_query` never sets `store`, so storage is implicit; "background mode stores response data for roughly 10 minutes to enable polling" (same doc). Not ZDR-compatible (VERIFIED, same doc) — irrelevant to this personal subscription.
- **Caching + background**: **no documented restriction either way** (checked the background guide, Azure caching doc, cookbook — all silent). The Azure caching doc scopes caching to "chat completions or response creation requests" without excluding background. Treat as expected-to-work, **UNCERTAIN** until we read `usage.input_tokens_details.cached_tokens` off a live background response (that field appears on Azure Responses objects — visible in [MS Learn reasoning doc](https://learn.microsoft.com/en-us/azure/ai-foundry/openai/how-to/reasoning) output dumps, VERIFIED).
- **Reasoning items / encrypted content**: `reasoning.encrypted_content` and `include` gymnastics only matter for **multi-turn** stateless reuse (`store=false`). Every one of our calls is single-turn — `mutate.py` sends one `instructions` + one `input` string, `msg_history=[]` even on the legacy path (`mutate.py:257`) — so no reasoning items cross calls and no restriction applies. The cookbook's note that chat completions "does not persist hidden chain-of-thought tokens between turns" and that Responses+`previous_response_id` gets "40-80% better cache utilization" (VERIFIED quotes) is about conversation chaining we don't do.

## 5. Multi-sample (K per prompt)

- **The Responses API has no `n` parameter** — VERIFIED-absent two ways: it is not in the request-parameter list of the installed SDK (`openai` 2.41.0, `miniconda3/envs/shinka/Lib/site-packages/openai/types/responses/response_create_params.py` — which DOES carry `background`, `store`, `previous_response_id`, `prompt_cache_key`, `prompt_cache_retention`, `safety_identifier`), nor in any Azure response dump. **K samples = K separate requests** on our transport, full stop.
- Chat completions `n`: the SDK's `chat/completion_create_params.py:158` does expose `n: Optional[int]`, but this is moot for us — we don't use chat completions, and per the [Azure reasoning-models feature table](https://learn.microsoft.com/en-us/azure/ai-foundry/openai/how-to/reasoning), `gpt-5.4-pro` and `gpt-5.3-codex` have **no Chat Completions API support at all** (Responses-only; VERIFIED — dashes in the feature table). Whether gpt-5.5 chat completions accepts `n>1` is UNCERTAIN (the "Not Supported" list for reasoning models names `temperature, top_p, presence_penalty, frequency_penalty, logprobs, top_logprobs, logit_bias, max_tokens` — VERIFIED exact — but not `n`).
- **No server-side "K samples per prompt" primitive exists.** Prompt caching is precisely the mitigation: K requests sharing a warmed prefix pay full input once and ~discounted input K−1 times.
- **Azure Global Batch**: "a 24-hour target turnaround at 50% less cost than global standard"; "Currently the completion window must be set to `24h`. If you set any other value than `24h` your job will fail." ([MS Learn batch doc](https://learn.microsoft.com/en-us/azure/ai-foundry/openai/how-to/batch), VERIFIED). **Useless for the inner loop** — a window needs results in minutes, not a day.

## 6. Our prompt shape vs. cache-friendliness

Effective prompt = `instructions` (=`patch_sys`) then `input` (=`patch_msg`) (`_azure.py:104-109`). Composition (`shinka/core/sampler.py:79-241`, `orchestrator/scripts/construct_mutation_prompt.py:116-176`):

1. `patch_sys` **starts** with `task_sys_msg` (sampler.py:90-93) — the only content stable across *all* mutations. Then, **before** the format block: per-attempt "# Direction for this attempt" (island brief / meta recs, sampler.py:136-147; or, when no direction was sampled on a diff/full gen, `EXPERT_CREATIVE_PREAMBLE`, sampler.py:148-149), failure note (155-161), then `DIFF_SYS_FORMAT`/`FULL_SYS_FORMATS[random]`/`CROSS_SYS_FORMAT` (163-172) — **the full-rewrite format variant is randomly sampled per call** (sampler.py:168), injecting noise into the system prompt tail. Then optional `extra_guidance` and the conditional runtime-budget caution (construct_mutation_prompt.py:129-131,164-176).
2. `patch_msg` starts with `eval_history_msg` (inspiration programs — differ per call), then parent code (sampler.py:237-241).

**Verdict**: the guaranteed shared prefix is exactly `task_sys_msg`. If it clears ~1,024 tokens, concurrent mutations (after warming) get hits on that slice only; everything after the first divergence (direction header) is uncached. Within one island+window, calls sharing the same direction, failure note, and patch type share a much longer prefix — but the random full-format variant and per-call cautions break it. Field-ordering rules that matter (Azure doc): tools (we send none on mutations) and structured-output schemas are prefixed to system; static content first. Concrete levers if we fan out: (a) make `task_sys_msg` + objective brief comfortably >1,024 tokens; (b) move per-attempt direction/failure-note **after** the format block, or into `input`; (c) pin one FULL format variant per window; (d) set `prompt_cache_key` (e.g., `run_id:island`) — the parameter exists on Azure Responses objects (`"prompt_cache_key": null` in [MS Learn reasoning doc](https://learn.microsoft.com/en-us/azure/ai-foundry/openai/how-to/reasoning) dumps, VERIFIED) and in the installed SDK's Responses create params. `metadata` (our `purpose`/`run_id`/`generation`, `mutate.py:222-226`) is not model input and shouldn't affect the prefix hash (UNCERTAIN — undocumented).

## 7. Ledger side-effect finding

Cache hits change **billing** but our ledger prices every input token at full rate: `_usage_cost` (`_azure.py:69-96`) and `get_openai_costs` (`openai.py:62-101`) ignore `input_tokens_details.cached_tokens`, and `pricing.csv`/`calculate_cost` carry no cached rate. Today (sequential, mostly-cold, mutation input dominated by per-call-unique code) the error is small; under a deliberate shared-prefix fan-out the ledger would **overcount** spend against `budget_usd` — conservative direction (stops early, never overspends), but worth wiring `cached_tokens` into `calculate_cost` before relying on caching economics.
