## 2. LOST-DESIGN FINDINGS (ranked by likely impact on search quality)

1. **Rolling meta scratchpad (cross-window insight accumulation).** Upstream's summarizer kept a persistent global-insights scratchpad that each meta round *updated*; the fork's per-window meta re-derives everything from archive rows (`meta_n_recent=32` + code previews) each time. Long-horizon lessons ("approach X was tried in windows 2–4 and always times out") can fall out of the 32-row recency window and be re-proposed. Only the one-line `failure_note` persists. Highest-leverage loss because the whole fork design leans on this single meta call per window.
2. **Parallel evaluation throughput.** Upstream ran 4 evals + 6 proposals concurrently in a stale-archive steady-state EA; the fork is fully serial. With `eval_time` up to 35 min, a 10-slot window can take ~6 h. This is a wall-clock loss, not a search-*quality* loss per candidate — but fewer candidates per day at fixed budget-time is fewer shots on goal.
3. **Alternative parent-selection strategies (`power_law`, `beam_search`).** The weighted sigmoid sampler is a good default, but when an island's scores compress (MAD→0) it approaches uniform-over-archive with only the children-count bonus differentiating; upstream offered power_law (rank-based, scale-free) as the escape. Fork has no switch — the code path is simply absent.
4. **Stdout truncation escape hatch.** Fix prompts embed raw `stdout_log`; a chatty evaluator (or a candidate that prints per-trial lines) can inflate a fix prompt by megabytes → token cost + drowned error signal. Upstream had `max_stdout_log_chars`; fork removed it without a replacement on the stdout axis.
5. **EVOLVE-marker post-validation.** Without it, one bad full-rewrite that drops the markers poisons the lineage for diff patches (all subsequent diff applies fail → apply-retry burn → slot dropped). Low frequency, annoying when it hits.
6. **SKILL.md-taught island-policy gates that don't reach the policy.** Not upstream parity strictly, but found during the knob audit: `policy_migrate_enabled` & co. read from the *call payload* with db_config-derived defaults, yet run_window forwards only `policy_spawn_cooldown` — so as `evo.*` keys they silently no-op. A knob that lies is worse than no knob.
7. *(Non-losses worth stating: temperature sampling — moot for an all-reasoning-model pool; novelty LLM judge — upstream shipped it off; oversubscription EWMA — moot for a serial driver; `exploitation_ratio` — dead upstream too.)*

## 3. PROPOSALS (ranked by value-for-effort)

**P1 — Restore a rolling meta scratchpad inside the per-window meta round. [B], effort S–M.**
What: extend `orchestrator/scripts/meta_summarize.py` (MUTABLE) to (a) carry a persistent `global_insights` text blob — store it beside `failure_note` in the journal/meta output the same way `meta_failure_note` is re-hydrated at boot (`run_window.py:1305-1308` pattern; no schema change: it rides the meta call's logged JSON, not sqlite) — and (b) include the previous blob in the meta prompt with the instruction "update, don't regrow; keep ≤ N lines; drop stale entries". Default: on.
Benefit: cross-window memory of what failed/worked survives past the 32-row archive window; directly upstreamed design (`summarizer.py`'s `meta_scratch_pad`).
Risk: blob bloat / staleness → cap length in-prompt and let each meta round rewrite it wholesale (self-pruning). If a measure window shows meta_health degradation, the standard strategy-rollback reverts it.
Outer-loop guidance (SKILL.md): at a control-return, *read* the scratchpad as a diagnostic; if it has collapsed into repetition, rewrite the pruning instruction — do not hand-edit the blob content itself.

**P2 — Make the knob surface honest: document pass-through DatabaseConfig knobs; fix or un-teach the island-policy gates. [A] for docs + [C]-small for wiring, effort S.**
What: (a) SKILL.md config-lever table: add rows for `db_config.num_archive_inspirations`, `num_top_k_inspirations`, `island_selection_strategy`, `migration_rate`/`migration_interval`, `island_elitism` — all already functional via `DatabaseConfig(**db_config)`, just undocumented as levers. (b) Either thread `evo.policy_migrate_enabled`/`policy_migrate_interval`/`policy_spawn_enabled`/`policy_spawn_stagnation` through run_window's window-boundary call (`run_window.py:1414-1423`; run_window is immutable mid-run → between-runs [C], ~10 lines), or delete those four rows from SKILL.md until wired. Do (b)'s doc fix immediately, the wiring between runs.
Benefit: the outer loop stops "flipping" levers that do nothing; migration becomes actually reachable as a config lever (today the only honest route is `db_config.migration_rate>0`, which drives the add()-time path).
Risk: none for docs; wiring risk is a behavior change in a foundation file — do it between runs with the smoke test.
Outer-loop guidance: consider `migration_rate: 0.1` (with `migration_interval: 10`) at a control-return when ≥2 islands are healthy but one is stagnant and its brief directions repeat — migration is the cheapest diversity injection that isn't a discovery round.

**P3 — Stdout cap where it enters prompts. [B], effort S.**
What: in `orchestrator/scripts/construct_mutation_prompt.py` (MUTABLE), head+tail-truncate `metadata.stdout_log`/`stderr_log` to 16KB before delegating to `sampler.sample_fix` (mirror `shinka/utils/general.py:17` constants). Do NOT re-add the upstream `max_stdout_log_chars` DB-side knob — truncating at prompt-build keeps the archive lossless.
Default: 16KB head+tail. Benefit: bounded fix-prompt cost, error signal not drowned. Risk: clipping the one informative middle line — head+tail split mitigates, same trade upstream made.
Outer-loop guidance: if fix rounds keep failing on a task whose evaluator prints diagnostics mid-stream, raise the cap in the strategy file for that run (it's exactly the mutable-prompt concern the audit hat owns).

**P4 — `parent_selection_strategy` dispatch in the parent sampler. [B], effort S–M.**
What: add a `power_law` branch to `orchestrator/scripts/sample_parent.py` (rank-based `P(i) ∝ (i+1)^-α`, α from `db_config.exploitation_alpha`, port of upstream `parents.py:105-195` with a parity test alongside the existing weighted-parity test). Skip `beam_search` — its value depended on the async runner's beam-state sync; serial windows don't amortize it.
Default: keep `"weighted"`. Benefit: an escape hatch when sigmoid weights flatten (score compression) or over-concentrate.
Risk: two code paths to keep parity-tested; mitigated by the existing test harness pattern (`orchestrator/tests/test_parity.py`).
Outer-loop guidance: flip `db_config.parent_selection_strategy` to `"power_law"` (α≈1.5–2) at a control-return when diagnostics show parent picks ~uniform across the archive (score MAD near zero) while the top-3 lineages are clearly better — i.e., exploitation is being diluted; flip back once spread returns.

**P5 — Bump inspiration counts. [A], effort S.**
What: set `db_config.num_archive_inspirations: 2, num_top_k_inspirations: 2` in `configs/orchestrator_run.default.json` (upstream default is 1/1, so this is a deliberate *departure*, not parity — flagging honestly).
Benefit: 4 exemplars instead of 2 per mutation prompt; brief-directed mode gets more assigned exemplars per direction. Cost: bigger prompts (full code per exemplar, no truncation) — roughly +2 programs × program size per call.
Risk: token spend on large programs → keep 1/1 for tasks whose programs exceed ~500 lines.
Outer-loop guidance: raise when mutations look context-starved (children repeat mistakes visible in unshown archive members); lower when per-call cost spikes on a big-program task.

**P6 — Re-add EVOLVE-marker post-validation. [C], effort S, between runs.**
What: restore a minimal `validate_evolve_markers` check after apply in `mutate.py`'s apply path (body immutable → foundation edit) or in `shinka/edit/apply_full.py`, treating a marker-count mismatch as `applied:false` so the existing apply-retry loop handles it.
Benefit: stops silent lineage poisoning. Risk: false rejects on legitimate marker-adjacent edits — restrict the check to "same number of begin/end markers as parent".

**P7 — Leave parallel evaluation dropped for now; revisit as [C]-L only if wall-clock becomes the binding constraint.**
Rationale: the serial driver is load-bearing for the fork's three hardest guarantees — crash-durable single-writer cost ledger, one-lock-per-results_dir, and the orchestrator's control-return semantics. Upstream's stale-archive steady-state EA is fine science, but reintroducing it means concurrent `archive_record` writers and concurrent cost booking, i.e., a rewrite of the foundation contract. The cheap 80% version if ever needed: overlap *eval k* with *proposal k+1* only (two stages, one in flight each) — still a [C]-L foundation change. Do not attempt as a strategy-file rewrite.

**Do NOT adopt (with rationale):**
- **Novelty LLM judge** — upstream ships it off; the fork's keep-the-better embedding gate already dominates it for this use (a *better-scoring* near-dup should replace, not be adjudicated). Re-adding costs one LLM call per near-dup for a worse decision rule.
- **Temperature sampling** — the entire fork pool is reasoning models for which upstream itself omitted temperature; the `model@effort` bandit arms are the working replacement for output-diversity control.
- **Prompt-evolution subsystem** — replaced by the framework-audit snapshot→deploy→measure→revert cycle, which has rollback; a self-mutating prompt DB inside a run would fight the strategy-fingerprint machinery.
- **Oversubscription / EWMA pipeline knobs, `exploitation_ratio`** — moot (serial) and dead-upstream respectively.
- **`use_text_feedback=False`, run-level early-stop knobs** — both would violate CLAUDE.md invariants (feedback always on; exactly three termination criteria).
- **Hydra/CLI/WebUI/multi-provider** — out of scope by design.

[B], ~3 lines.)*
